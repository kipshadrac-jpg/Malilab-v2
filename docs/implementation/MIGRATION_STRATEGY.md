# Migration Strategy

Conceptual only. No migration files are created or run.

1. **Before initial migration:** use the owner-approved custom Django user model with normalized unique email and email/password identity, verified-email state, email recovery and server-side sessions. Finalize field-level status/verification mechanics without changing policy. Preserve the hybrid deletion lifecycle with protected references and no account-wide cascade. Select exact Django version and PostgreSQL support in implementation planning. Age/eligibility and backup expiry remain TODO but do not alter account identity schema.
2. **Initial schema migration:** create account principal first; editorial identities/revisions and source governance; practice/calculations/planning; journey and learning evidence; discovery projection. Resolve circular current-revision pointers through nullable pointers populated after revisions exist. Use FK constraints and unique/check constraints from this specification.
3. **Reference data:** use reviewed, deterministic data migrations for controlled enums/initial system definitions only. Avoid embedding mutable editorial content in schema migrations.
4. **Editorial seed content:** import only owner-approved new MaliLab material using a separate idempotent seed/import process after content workflow exists. Do not import legacy data or legacy model assumptions.
5. **Formula seed:** formula artifacts begin Draft; a data migration may create definitions/versions but must never mark them Active. Activation requires test evidence, human review, a second-person approval and explicit activation record through governed workflow. Author/approver must differ for published financial content; staff MFA is required.
6. **Future schema changes:** additive nullable fields/tables first; backfill in bounded and idempotent data migrations; deploy compatible readers/writers; validate; then enforce non-null/unique constraints; remove obsolete fields only after an approved multi-release compatibility window.
7. **Historical snapshot migrations:** never rewrite immutable published revisions, Plan Revisions, Calculation Results or submitted attempts to match current rules. If transformation is required for rendering, retain original payload and record a new derived representation with schema/version provenance.
8. **Rollback:** schema rollback must not discard committed user history. Prefer forward repair for data migrations. Before destructive migrations, verified database and media backups plus documented restore path are mandatory. Code rollback does not reverse data transformation.
9. **Environments:** dev/staging/prod databases and media isolated; no production user data in fixtures. Production capacity, off-host backup and restore validation are deployment gates, not Phase 5 activity.

Email delivery configuration is needed for verification/recovery in a later implementation/deployment step; no provider, credential, or infrastructure is selected here. A verified account gates persistence; public content remains readable anonymously. Deletion is a dedicated service and data migration must never perform unreviewed account-wide cascades. Calculator migrations use KES as initial currency support and leave formula precision/ranges to individually approved calculator definitions.
