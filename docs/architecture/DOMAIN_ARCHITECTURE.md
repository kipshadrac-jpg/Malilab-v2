# Domain Architecture

**Status:** Accepted logical boundaries for the modular monolith. These are domains, not proposed microservices; physical organization remains for implementation design.

## Boundary rules

- Each domain owns its records and lifecycle. Other domains use its application-level capabilities rather than directly changing its data.
- One PostgreSQL transaction may coordinate related writes in the initial monolith.
- Shared concepts such as account identity and content-version identifiers are references, not permission to own another domain's lifecycle.
- User-owned financial information is isolated from editorial content and admin workflows.
- An item marked “initial” belongs in the initial application boundary; “deferred” is a documented extension, not a hidden requirement.

## Important workflows and ownership

### Publish content

Content Administration → Editorial Workflow → Editorial Content publishes a new immutable version. Search indexes only the selected published version. The content domain owns canonical content and revisions; Search owns a rebuildable projection.

### Save an exploratory plan attempt

Identity verifies user; Practice/My Plan validates ownership and request shape; Calculation Engine computes from explicit input snapshot; Scenario/Assumption preserves relevant assumptions/results; My Plan records a new immutable revision and emits a fact/evidence record; Progress consumes that evidence. My Plan works even if Progress is unavailable. A write to one user's data cannot be performed by supplying another user's identifier.

### Versioned learning completion

For a specific Module revision, Learning Delivery reads its requirement set. Progress evaluates facts for every required Lesson and required Practice in that set, preserves the exact satisfied/missing item evidence, and explains completion against that revision. Optional/recommended Lessons and optional/recommended Practice do not block completion. An owner-approved completion rule for each activity remains necessary before implementation.

### Preserve originating Playbook context

When a learning path begins at a Playbook, a Learning Journey Context refers to the exact published Playbook revision and the revision-specific recommendation link followed. It can be associated with later Module/Lesson study, Practice attempts, plan revisions, and Progress evidence. The context references editorial revisions and assumptions; it does not copy Playbook content.

## Dependency direction

The dependency is one way: **Learning Delivery / Practice / My Plan produce facts and evidence → Progress consumes and explains them → Achievements may consume qualifying Progress evidence.** My Plan never requires a Progress call to save, revise, or calculate a plan. In the monolith, an application-level workflow may coordinate writes transactionally, but domain dependencies remain acyclic; no distributed event bus is required.

## Search validation

Before accepting the PostgreSQL search candidate, test representative queries against a small reviewed set of published Playbooks/Modules/Lessons. Include English queries, Kenyan financial terms, abbreviation expansions, spelling variants, and natural user phrasing (e.g., finding a savings/income target by a question rather than a product name). Candidate vocabulary should include terms such as Treasury Bill/T-bill, Treasury Bond/T-bond, SACCO, MMF/Money Market Fund, CDS account, CRB, yield, and coupon, with plausible spacing/plural/typo variants. Confirm relevant results are discoverable, unpublished drafts/private data never appear, and indexing updates after publish/retire.

Exact queries, supported languages, relevance expectations, and acceptance thresholds are TODO/TO-BE-DEFINED. Consider dedicated search only when tuning/query expansion and indexing cannot meet approved relevance/language requirements, or measured latency/index load exceeds approved targets. Do not select or install a search engine now.

### Preserve a learning reference

Notes, Progress, and saved calculations point to stable content-version and, where useful, block identifiers. Editorial Content retains old versions according to policy. If old content is retired, the private historical context remains distinguishable from current public content.

## Deliberately excluded boundaries

No separate microservice per domain; no generic knowledge-graph service initially; no general chatbot/financial-advice domain; no payment/entitlement domain in initial scope; no notification service; no audio/media pipeline; no public API consumer domain. Revisit only from approved requirements and operational evidence.
