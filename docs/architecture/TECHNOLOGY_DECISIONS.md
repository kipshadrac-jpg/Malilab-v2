# Technology Evaluation and Recommendations

**Status:** Phase 3 architecture approved with refinements. Recommendations marked Accepted below are architecture direction only; Proposed and Deferred items remain unresolved. No tools or packages were installed, and supported versions will be selected during implementation planning.

Status summary: **Accepted** — Django modular monolith, PostgreSQL, server-rendered frontend, same-origin capability interfaces, deterministic calculation service, and session-based application authorization without initial RLS. **Proposed** — PostgreSQL search candidate pending representative-query validation; local persistent media pending capacity/backup validation. **Deferred** — dedicated search, cache, worker/queue, object storage/CDN, public API, managed identity, and physical deployment topology unless evidence triggers them. **TODO/TO-BE-DEFINED** — exact language/framework versions, login/account policy, capacity/SLOs, and search acceptance criteria.

## Evaluation basis

Requirements: Playbook-led editorial discovery; long-form structured reading; internal content administration and human review; authenticated user-owned notes/plans/progress; deterministic calculations; relational content links and immutable versions; initial single-team scale; Oracle Linux 9 x86_64 target; low operational complexity. ## Backend and module implementation shape (future, not code)

Organize the eventual Django project by domain modules: accounts, content, editorial, discovery, learning/practice, calculations/scenarios, plans, notes, progress/achievements, and assets. Each provides application services and explicit authorization. Presentation views call these services. Shared schema can exist in one DB, but importing another domain's internal model to mutate it should be avoided. This is a logical organization recommendation, not a generated package layout.

## Migration and upgrade implications

- PostgreSQL schema changes will be delivered through reviewed migrations in later phases; use additive/expand-contract changes when deployed data must survive.
- Content versions and formula versions preserve historical meaning across code/content updates; calculator results are not silently recalculated on upgrade.
- Keep search projection rebuildable from current published revisions so search-engine changes do not require rewriting canonical content.
- Keep media locators behind a storage adapter so local-to-object storage migration does not alter content identity.
- Avoid introducing Redis, a queue, a microservice boundary, or public API until a documented trigger justifies its ongoing operations and migration cost.
- Pin supported versions during implementation and schedule security updates; this architecture does not select a version number.

## Search validation before production use

Use a small reviewed corpus of current published Playbooks, Modules, and Lessons. Build candidate queries in English, include Kenyan financial terms (for example Treasury Bill/T-bill, SACCO, MMF/Money Market Fund, CDS account, CRB, yield/coupon), likely spacing/spelling variants, abbreviations, and natural questions such as how much to save monthly or how to replace income. Include approved Swahili/Kenyan-language queries if those languages are selected. Review whether relevant results appear, whether drafts/private data are excluded, and whether publish/retire updates appear correctly. Exact query set and success thresholds are TODO/TO-BE-DEFINED; do not infer supported languages or guarantee relevance. Consider a dedicated search system only when database search cannot meet approved quality, language, latency, or scale goals after tuning.
